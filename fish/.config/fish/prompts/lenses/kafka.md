Kafka lens. Producers, consumers and stream processors on Kafka — Java (`kafka-clients`, Spring Kafka, Reactor Kafka), Rust (`rdkafka`), Go (`confluent-kafka-go`, `segmentio/kafka-go`, `IBM/sarama`, `franz-go`). The defect is a delivery guarantee the code believes it has and doesn't: a lost record, a duplicate with a non-idempotent effect, an order that isn't preserved, a consumer stuck or kicked out of its group. The broker's semantics are the same from every client; the client section below covers what differs.

HARD GATE: for every finding, name the event that triggers it — a crash between process and commit, a rebalance, a leader failover, a slow batch over the poll interval, a record that can't be deserialized, a retry — and what the system then does: loses the record, processes it twice with a visible effect, reorders it, stops consuming. If the handler is shown to be idempotent, at-least-once duplicates are NOT a finding.

Where to look first (non-exhaustive — reason beyond this list). Config names are the Java / librdkafka ones (`rdkafka`, `confluent-kafka-go` use them as is); native Go clients have equivalent options:
- Commit vs processing: auto-commit (`enable.auto.commit`) commits on a timer whatever was processed (crash → loss or replay); committing before the work is done — or before work handed to a thread, task, goroutine or reactive chain finishes — loses records; the committed offset must be last processed + 1.
- At-least-once without idempotency: a redelivered record repeats a DB insert, a payment, an email — no dedupe key, no upsert, no processed-offset table.
- Rebalances: a batch processed longer than `max.poll.interval.ms` gets the consumer kicked out and its records redelivered to another member; no commit of processed offsets when partitions are revoked; a handler that ignores revocation keeps working on partitions it no longer owns.
- Producer durability: `acks=0/1` loses acknowledged records on leader failover (needs `acks=all` + `min.insync.replicas>=2`); every client's send is asynchronous — an ignored future, callback, delivery report or error channel hides every failure; no flush/close on shutdown drops buffered records.
- Ordering: only within a partition — a null or wrong key scatters one entity's events; retries with several in-flight requests and idempotence off reorder; adding partitions remaps keys; producers in different languages hashing keys differently put the same key in different partitions.
- Poison records: a deserialization failure in the poll loop is retried forever and blocks the partition; no dead-letter path; tombstones (null value on a compacted topic) hitting code that assumes a value.
- Exactly-once claims: consume-transform-produce without committing the input offsets inside the producer transaction; consumers on `read_uncommitted` see aborted records; Kafka transactions never cover DB writes or HTTP calls.
- Consumer group config: one group id shared by two services splits their traffic; a new group starting at `latest` skips everything produced before its first start.

Client specifics:
- Java `kafka-clients`: `KafkaConsumer` is not thread-safe (only `wakeup()` is); `KafkaProducer` is, and should be shared, not created per send.
- Spring Kafka: `DefaultErrorHandler` retries then logs and SKIPS the record unless a `DeadLetterPublishingRecoverer` is set; poison deserialization needs `ErrorHandlingDeserializer`; with `AckMode.MANUAL*` a missing `ack.acknowledge()` commits nothing; `concurrency` above the partition count leaves threads idle; `JsonDeserializer` with trusted packages `*` deserializes any type from the header.
- Reactor Kafka: `ReceiverOffset.acknowledge()` before processing finishes acks unprocessed records; `flatMap` over records breaks per-partition order (`concatMap` / group by partition); an error terminates the receiver Flux and closes the consumer — without a restart (`retryWhen`/resubscribe) consumption stops for good.
- Rust `rdkafka`: with auto-commit on, offsets are stored as soon as a message reaches the app — set `enable.auto.offset.store=false` and `store_offset_from_message` after processing; committing right after `tokio::spawn` of the work commits unprocessed records; a `FutureProducer` send must be awaited, a `BaseProducer` needs `poll()` for its delivery callbacks; no `flush()` before drop loses the queue.
- Go `confluent-kafka-go` (librdkafka): `Produce` is asynchronous — the delivery report on `Events()` or the delivery channel must be read, and `Flush()` called before `Close()`; store offsets after processing (`enable.auto.offset.store=false` + `StoreMessage`).
- Go `segmentio/kafka-go`: `Reader.ReadMessage` with a group commits right away — process-then-commit needs `FetchMessage` + `CommitMessages`; a non-zero `CommitInterval` commits asynchronously and can lose the last commits; `Writer`'s default balancer is round-robin and ignores the key (`&kafka.Hash{}`; `ReferenceHash` to match Java's partitioning); set `RequiredAcks` explicitly; with `Async: true` errors are dropped unless `Completion` handles them; `Close()` flushes.
- Go `IBM/sarama`: `MarkMessage` only after processing (auto-commit commits what is marked); `ConsumeClaim` must return when `session.Context()` is done or the rebalance hangs; with `Return.Errors` / `Return.Successes` on, those channels must be drained or the client deadlocks; `Producer.RequiredAcks` defaults to `WaitForLocal`; the default hash partitioner is not Java-compatible (`NewReferenceHashPartitioner`).
- Go `franz-go`: default autocommit commits what was polled — process before the next poll, or `DisableAutoCommit` + `CommitRecords`; `ProduceSync` / a promise callback to see produce errors.

Not bugs:
- At-least-once with a handler the code shows is idempotent (upsert, dedupe key).
- Auto-commit in a consumer where loss is stated to be acceptable (metrics, logs); test and one-off tool code.
