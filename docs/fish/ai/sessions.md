## Overview

A session is a persistent chat history stored as an append-only JSONL file. Each user turn and each assistant response is appended as a typed JSON object. Resuming a session reconstructs the conversation in memory from the file.

**Ollama only.** Sessions are managed by this toolkit only when the resolved provider is Ollama. For Claude conversations, use Claude CLI's native session management (`claude --resume` / `claude -c`). The toolkit deliberately does not bridge to Claude's session storage — see [the architectural boundary](architecture.md#sessions-a-parallel-pipeline) for the reasoning.

Triggering a session with `--provider claude` (explicit or via task resolution) emits a clear error with the redirect.

## Storage layout

Sessions are stored at one of two locations, selected by walk-up resolution.

### Directory structure

```
<project-root>/
└── .ai/
    └── sessions/
        ├── debug-foo.jsonl         active session
        ├── refactor.jsonl          active session
        ├── .last                   pointer to most-recent session name
        └── archived/
            └── old-session.jsonl   archived (hidden from default ls)

~/.config/ai/
└── sessions/
    ├── general-chat.jsonl
    ├── .last
    └── archived/
```

### Walk-up resolution

For an existing session name, `_ai_session_file NAME`:

1. From `$PWD`, walk up checking each ancestor for `<dir>/.ai/sessions/NAME.jsonl`.
2. Stop at `$HOME` or `/` (don't search beyond the user's home).
3. Stop at any directory containing `.git/` (git root is the project boundary).
4. If not found in walk-up: try `~/.config/ai/sessions/NAME.jsonl`.

This is symmetric with [config walk-up](architecture.md#layer-3-configuration). Sessions and config use the same boundary rules.

### Write target for new sessions

`_ai_session_target NAME [SCOPE]`:

1. If walk-up finds an existing path: use it.
2. If `SCOPE = global`: `~/.config/ai/sessions/NAME.jsonl`.
3. Otherwise:
   - If in a git repo: `<git-root>/.ai/sessions/NAME.jsonl`.
   - Else: `<cwd>/.ai/sessions/NAME.jsonl`.

This means new sessions go to the project layer by default when you're in a repo, and `--global` is the opt-out for shell-wide sessions.

### `.last` pointer

A plain text file containing the name of the most recently used session in that directory. Used by `ai chat -c` (continue last). Updated automatically when a session is resumed or created. Cleared when the session it points to is deleted.

The walk-up for `.last` is the same as for session files — project's `.last` wins over global. So `cd` into a project, run `ai chat -c`, and you get that project's last session.

## JSONL format

Each line is one self-contained JSON object with a `t` (type) field. The file is append-only at runtime (commands that "modify" — `clear`, `edit`, `rename` — rewrite the file under the hood, but the runtime expectation for sessions in flight is append-only).

### Record types

| `t` | Required fields | Optional fields | Frequency |
|---|---|---|---|
| `meta` | `name`, `created`, `updated` | `title`, `branched_from`, `imported_from` | Exactly one, first line |
| `system` | `content` | `ts` | Zero or more; usually at file head |
| `user` | `content`, `ts` | — | Per user turn |
| `assistant` | `content`, `ts`, `model` | `usage` | Per response |
| `summary` | `content`, `ts`, `covers` | `model` | Generated by rolling summary |
| `config` | `pinned` | `provider`, `model`, `ts` | Generated by pin/unpin |

### Examples

A typical session start:

```jsonl
{"t":"meta","name":"debug-foo","created":"2026-06-15T19:00:00Z","updated":"2026-06-15T19:00:00Z"}
{"t":"system","content":"You are concise."}
{"t":"user","content":"What's the bug in Core.scala?","ts":"2026-06-15T19:00:01Z"}
{"t":"assistant","content":"Looking at line 142...","ts":"2026-06-15T19:00:03Z","model":"qwen3.5:9b","usage":{"prompt_eval_count":120,"eval_count":380,"total_duration":4123456789}}
```

After a rolling summary triggers:

```jsonl
{"t":"summary","content":"Alex works on Octopus (Scala). Main module: src/main/scala/octopus/Core.scala. Bug at line 142. Decision: use Option[String]. Pattern: follow Utils.scala matching.","ts":"2026-06-15T19:42:00Z","covers":4,"model":"qwen2.5-coder:7b"}
```

`covers` is a durable cursor: it says "the first 4 user/assistant turn records are folded into this summary". Future loads of the file skip those records and use the summary in their place.

After pinning:

```jsonl
{"t":"config","pinned":true,"provider":"ollama","model":"qwen2.5-coder:32b","ts":"2026-06-15T19:50:00Z"}
```

The latest `config` record wins. To revert, append `{"t":"config","pinned":false,...}`.

### What's in `usage`

For Ollama, taken from `/api/chat`'s done-chunk:

| Field | Meaning |
|---|---|
| `prompt_eval_count` | Tokens in the prompt portion |
| `eval_count` | Tokens in the response portion |
| `total_duration` | Nanoseconds for the whole call |

These are stored verbatim — `ai sessions info` and `ai sessions stats` aggregate them.

## Lifecycle operations

### Create / resume

`ai chat --session NAME` (or `-s NAME`):

```mermaid
flowchart TD
    start[ai chat -s NAME]
    walkup{walk-up finds<br/>existing file?}
    create[create new file<br/>at _ai_session_target]
    init[append {t:meta} row<br/>+ optional {t:system}]
    resume[load existing file]
    repl[enter REPL loop]
    update_last[write .last pointer]

    start --> walkup
    walkup -- yes --> resume
    walkup -- no --> create
    create --> init
    init --> repl
    resume --> repl
    repl --> update_last
```

If `--new` is specified and walk-up finds an existing file, error with the path. Useful for "I want a fresh session, don't accidentally resume."

If `--system "..."` is given, the system content is written only on first creation (existing sessions ignore it — to update, use `ai sessions edit`).

### Continue last (`-c`)

`ai chat -c`:

1. Read project's `.ai/sessions/.last` (walk-up). If exists and the named session exists, use it.
2. Else read global `~/.config/ai/sessions/.last`. If exists and points to an existing session, use it.
3. Else error.

`.last` pointing to a deleted session is treated as no pointer — falls through to global.

### Rename

`ai sessions rename OLD NEW`:

1. Resolve OLD via walk-up.
2. Validate NEW doesn't exist in the same directory.
3. `mv` the file.
4. Rewrite the first line: replace `meta.name` with NEW.
5. If `.last` in the same dir pointed at OLD, update to NEW.

Cross-scope rename (project → global rename in one step) is not supported — use `move` followed by `rename`.

### Move (between scopes)

`ai sessions move NAME --to {project|global}`:

1. Find source via walk-up.
2. Compute target dir: `~/.config/ai/sessions/` for `--to global`, or `<git-root>/.ai/sessions/` for `--to project`.
3. `--to project` outside a git repo: error (no project root to move into).
4. `mv` file.
5. If source dir's `.last` pointed at this session, clear source `.last`, write target `.last`.

If source and target paths are identical (e.g., session already in target scope), no-op with a message.

### Branch (fork)

`ai sessions branch SRC [NEW]`:

1. Resolve SRC.
2. If NEW omitted: auto-name `SRC-branch-N` where N is the smallest free number.
3. Copy file content to NEW location (same directory).
4. Rewrite first line: new `name`, fresh `created`/`updated`, add `branched_from: SRC` for traceability.

The branch starts from the full SRC history. To branch from an earlier point in time, use `ai sessions edit` to trim before branching.

### Archive / restore

`ai sessions archive NAME`:

- `mv NAME.jsonl archived/NAME.jsonl` (in the same scope's directory).
- Clear `.last` if it pointed at this session.

`ai sessions restore NAME`:

- Look in `archived/` (project walk-up then global) for `NAME.jsonl`.
- `mv` back up one level.
- Remove the now-empty `archived/` directory.

Archived sessions are hidden from default `ai sessions ls`. Show them with `ai sessions ls --archived` or `--all`.

### Clear

`ai sessions clear NAME`:

- Keep only the first line (`meta`).
- Drop all other records.

Use for "I want to reset this conversation but keep the name and timestamps." For total deletion, use `rm`.

### Delete

`ai sessions rm NAME`:

- Delete the file.
- If `.last` pointed at it in that directory, remove `.last`.

Prompts for confirmation unless `-f`/`--force` is passed.

## Context management

Long sessions risk overflowing the model's context window. The toolkit applies two strategies, in order:

1. **Rolling summary** — preferred. Summarize old turns into a `summary` block; future turns skip those raw records.
2. **Sliding window** — fallback. Drop oldest turns to fit the budget.

Both run automatically based on config thresholds.

### Decision flow

```mermaid
flowchart TD
    start["new user turn submitted"]
    measure["estimate tokens of head + uncovered turns"]
    in_budget{est ≤ budget?}
    pass["pass full history to model"]

    many_turns{"uncovered turns ><br/>2 × recent_turns + 1?"}
    summarize["maybe_summarize:<br/>generate summary,<br/>append {t:summary,covers:N}"]
    rebuild["recompute budget<br/>with summary in place"]
    still_over{est ≤ budget?}
    slide["sliding window:<br/>keep last 2N+1 turns"]
    aggressive["drop pairs from front<br/>until ≤ budget (min 3 left)"]
    call["call /api/chat with assembled messages"]

    start --> measure
    measure --> in_budget
    in_budget -- yes --> pass --> call
    in_budget -- no --> many_turns
    many_turns -- yes --> summarize --> rebuild --> still_over
    many_turns -- no --> slide --> still_over
    still_over -- yes --> aggressive --> call
    still_over -- no --> call
```

### Token estimation

Heuristic: `total_chars / 3`. Conservative overestimate to stay under-budget. Real tokens may be fewer; the model's actual `prompt_eval_count` (returned after the call and stored in `usage`) is the authoritative number.

### Budget

```
budget = floor(context_window × sessions_token_threshold)
```

Where:

- `context_window` is the model's native limit. Queried once per model via `/api/show` and cached in `~/.cache/ai-context-windows.json`. Fallback: 8192.
- `sessions_token_threshold` is a config knob (default `0.7`). Lower = more aggressive truncation.

### Sliding window

`keep_n = 2 × sessions_recent_turns + 1`

For example, with default `sessions_recent_turns=10`, the window keeps the last 21 messages (10 user + 10 assistant pairs + the current pending user). System and summary blocks are always preserved.

### Rolling summary

When triggered, summarize the **front portion** of uncovered turns (`uncovered_count - keep_n` records). Append a `{t:"summary", covers:N}` record. Future `build_messages` calls skip the first N user/assistant records, using the summary as a system message instead.

`covers` is cumulative. If a second summary triggers later, it has a larger `covers` value, covering all turns summarized so far (including by previous summaries — though in practice each summary covers only what was added since the last one).

The summarization model is configurable:

```
sessions_summary_model=qwen3.5:9b    # config key; default = current session's model
```

The summarize call uses the prompt template at `~/.config/fish/prompts/meta-session-summary.md`. Edit it to tune output structure.

### Config knobs

| Key | Default | Effect |
|---|---|---|
| `sessions_recent_turns` | 10 | Target window size (user+assistant pairs to keep verbatim) |
| `sessions_token_threshold` | 0.7 | Fraction of context window before truncation kicks in |
| `sessions_summary_model` | (current model) | Model used for the summarize call |

Set in `~/.config/ai/config` for global, `<project>/.ai/config` for per-project. See [Configuration in toolkit.md](toolkit.md#configuration).

### Side-effect separation

The pipeline keeps state mutation explicit:

- `_ai_session_maybe_summarize FILE MODEL` — side effect: may write a `summary` record to FILE. Called first.
- `_ai_session_build_messages FILE MODEL` — pure: reads FILE, emits a messages JSON array suitable for `/api/chat`. Called second.

This separation means `build_messages` can be unit-tested independently and called from other contexts (e.g., a future export tool) without triggering API calls.

## Pinning

A session can be **pinned** to a specific provider and/or model. On resume, the pinned config beats task-level resolution.

### Pin

```
ai sessions pin NAME --provider ollama --model qwen2.5-coder:32b
ai sessions pin NAME --model qwen2.5-coder:32b      # provider unchanged
ai sessions pin NAME --provider claude              # ⚠ session becomes invalid (claude is ollama-only)
```

Appends `{"t":"config", "pinned":true, "provider":..., "model":..., "ts":...}` to the file.

### Unpin

```
ai sessions unpin NAME
```

Appends `{"t":"config", "pinned":false, "ts":...}`. Future resumes will fall back to task-level resolution.

### Resolve order on resume

```
1. --model flag passed at run time (highest)
2. latest {t:"config", pinned:true} record (if any)
3. _ai_default_model chat ollama (task resolver)
```

The header shows `[pinned]` next to the model name when a pin is active. Use `ai sessions ls` to see pin status across all sessions (also marked `[pinned]`).

### Why pin

- Lock a long-running session to a model you trust for that domain.
- Prevent accidental task-level config changes from affecting an in-progress conversation.
- Use a specialized model (e.g. `qwen2.5-coder:32b`) for coding sessions while keeping `chat` task resolved to a smaller chat model.

## Concurrency

Two terminals open with the same session both append to the same JSONL file.

### What's safe

- **Reads.** `jq -sc` slurps the file; concurrent reads have no contention.
- **Appends of single records < 4KB.** POSIX guarantees `write(2)` atomicity for sizes below `PIPE_BUF` (4KB on macOS, 4KB on Linux). A typical turn message fits well within this. Each `_ai_session_chat` invocation appends one record at a time, so two terminals appending each will produce a coherent file with both records.

### What's not guaranteed

- **Large messages (> 4KB).** Theoretically possible for two terminals' assistant responses to interleave at the byte level. In practice this is very rare — the file already has plenty of records before this becomes a concern.
- **Operations that rewrite the file** (`clear`, `rename`, `branch`). These are not atomic with respect to concurrent runtime appends. If you're rewriting, no terminals should be actively chatting in that session.

### Detecting corruption

If `jq -sc '.' <file>` errors, the file has corrupt JSONL. Manually fix by removing the offending line(s) or restoring from a backup.

For a fully serialized workflow, use `flock` around critical operations. Not enabled by default — the cost rarely justifies it for personal sessions.

## Search and stats

### `ai sessions search QUERY`

Case-insensitive substring search over **user and assistant** message content. System prompts, summaries, and meta are not searched.

```
ai sessions search "migration"
ai sessions search "Option[String]" --name "refactor*"
ai sessions search "marina" --since 2026-05-01
ai sessions search "fix" --all                       # include archived
```

Output: matching messages with session name, scope, and timestamp context. Multiple matches per session shown as separate Turn-N lines.

Filters:

| Flag | Effect |
|---|---|
| `--name PATTERN` | Substring match on session name (not glob) |
| `--since YYYY-MM-DD` | Filter to sessions updated on/after this date |
| `--archived` | Search only archived sessions |
| `-a`, `--all` | Include both active and archived |

### `ai sessions stats`

Aggregated counts across all visible sessions.

```
ai sessions stats                    project + global active sessions
ai sessions stats --all              include archived
```

Output includes total sessions, total assistant turns, total tokens (input + output), oldest/newest activity, and a breakdown of models used by turn count.

### What's NOT in stats

- Per-session breakdown — use `ai sessions info NAME` for one session.
- Cost — not computed. Ollama is local (no cost); for hypothetical Claude API tracking, you'd need API mode (not currently supported).

## Token tracking

Each `assistant` record stores its `usage` data from the API. `ai sessions info` and `ai sessions stats` sum these to produce token counts.

### Per-session

```
ai sessions info debug-foo
```

Output includes:

- Path, scope, dates
- Turn count (assistant turns)
- Tokens: input / output
- Models used

### Aggregated

```
ai sessions stats
```

Sums across all sessions in scope.

### Limitations

- Token counts come from Ollama's `/api/chat` response. Reliable for that backend.
- The `total_duration` field is also stored but not currently surfaced in info/stats output.
- Pre-summary turns: the tokens for the summarize call itself are not stored (summarization is a separate call). If you want strict accounting, this is a known gap.

## Editing the raw file

`ai sessions edit NAME` opens the JSONL in `$EDITOR` (falling back to `nvim`/`vim`). Use cases:

- Fix typos in your messages
- Add/update system prompt
- Remove a misleading turn
- Add a manual summary
- Trim history before forking

### Guidelines

- **Preserve the first line as `meta`.** Tools depend on it.
- **Keep one JSON object per line.** No multi-line objects.
- **Don't break timestamps unless you mean to.** Stats parse them.
- **If you delete a turn, consider** whether downstream `covers` values still make sense. If a summary's `covers` no longer matches reality, edit it too.

### After editing

The next REPL run reads the file fresh. No reload command.

For batch edits across sessions, scripting against the jsonl files directly with `jq` is fine — the format is stable and documented above.

## Backup and migration

### Export

```
ai sessions export NAME                       # md to stdout
ai sessions export NAME -f json               # full JSON array to stdout
ai sessions export NAME -f jsonl              # raw copy
ai sessions export NAME -f md ~/notes/sess.md # write to file
```

Formats:

| `-f` value | What |
|---|---|
| `md` | Rendered markdown (the same view as `ai sessions show`) |
| `json` | Full slurped JSON array (lossless) |
| `jsonl` | Raw file copy (lossless) |

For backup, use `jsonl` or `json` — both preserve all metadata.

### Import

```
ai sessions import path/to/file.jsonl                  # default scope
ai sessions import path/to/file.jsonl --name new-name  # rename on import
ai sessions import path/to/file.jsonl --global         # force global scope
```

The first line must be a `meta` record. If `--name` is given, the file is rewritten with the new name in `meta`.

### Cross-machine sync

Sessions are plain text files in known locations. Sync `~/.config/ai/sessions/` or `<project>/.ai/sessions/` via any file sync mechanism (rsync, syncthing, git). No locks, no DB, no special handling required.

For `<project>/.ai/sessions/`: typically gitignored (personal context). Commit only if intentionally shared with the team.

## Common workflows

Brief patterns. For longer scenarios with rationale, see [howto.md](howto.md).

### "Continue what I was working on"

```
ai chat -c
```

### "Fresh session for a different topic in this project"

```
ai chat -s refactor-auth --new
```

### "Same conversation, but switch to a heavier model for one turn"

```
ai chat -c --model qwen2.5-coder:32b
```

(Model used for that turn only; doesn't persist.)

### "Lock this session to a model permanently"

```
ai sessions pin debug-foo --model qwen2.5-coder:32b
```

### "Fork the current session to try a different direction"

```
ai sessions branch debug-foo
ai chat -s debug-foo-branch-1
```

### "I'm done with this session for now but don't want to delete it"

```
ai sessions archive debug-foo
```

Restore later with `ai sessions restore debug-foo`.

### "Promote a personal session to be team-visible"

```
ai sessions move debug-foo --to project
git add .ai/sessions/debug-foo.jsonl  # if you want to commit
```

### "Find every conversation that mentioned X"

```
ai sessions search "X" --all
```

### "Export a session as a markdown post-mortem"

```
ai sessions export debug-foo -f md > docs/postmortems/foo.md
```
